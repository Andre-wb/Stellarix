## 1. Идея и архитектурный подход

Stellarix — гибридное приложение: внутри Tauri-обёртки крутится полноценный
Rust-веб-сервер (Axum + Postgres), который рендерит обычные HTML-страницы
и отдаёт их в системный WebView того же самого приложения. То есть с точки
зрения фронтенда это «сайт», но открывается он не в браузере, а в
десктопном окне, и у него есть привилегированный мост в нативный слой
(`window.__TAURI__`) для доступа к микрофону/динамику на уровне ОС.

Это решает главную проблему передачи данных звуком: браузерный `Web Audio
API` слишком высокоуровневый и с задержками не годится для точной
демодуляции OFDM-сигнала в реальном времени, поэтому вся DSP-логика вынесена
в нативный Rust-код (`cpal` + собственный OFDM-модем), а Tauri-команды
(`play_payload`, `send_file`, `start_listening`, …) вызываются из JS как
обычные асинхронные функции.

Архитектура состоит из четырёх слоёв:

```
┌─────────────────────────────────────────────────────────────┐
│  Tauri Shell (WebView + нативное окно, автозапуск процессов)│
│  ┌─────────────────────────┐   ┌────────────────────────┐   │
│  │   Frontend (HTML/CSS/JS) │   │  Tauri commands (Rust)  │   │
│  │  - шаблоны Askama        │◄─►│  - play_payload          │   │
│  │  - E2E-крипто в браузере │   │  - send_file             │   │
│  │  - UI чата/дашборда      │   │  - start/stop_listening  │   │
│  └───────────┬───────────────┘   └──────────┬─────────────┘   │
│              │ HTTP (127.0.0.1:8000)          │ cpal (аудио)   │
│  ┌───────────▼───────────────┐   ┌──────────▼─────────────┐   │
│  │   Axum веб-сервер (Rust)   │   │  Модем: OFDM + ARQ (Rust)│  │
│  │  - маршруты, сессии        │   │  - модуляция/демодуляция│  │
│  │  - Askama-рендеринг        │   │  - adaptive rate control│  │
│  │  - REST /api/stats         │   │  - файловая политика     │  │
│  └───────────┬───────────────┘   └──────────────────────────┘  │
│              │ sqlx                                            │
│  ┌───────────▼───────────────┐                                 │
│  │  Embedded PostgreSQL        │  (управляется процессом, не   │
│  │  (postgresql_embedded)      │   требует установки СУБД)     │
│  └─────────────────────────────┘                                │
└─────────────────────────────────────────────────────────────┘
```

Ключевое архитектурное решение: **приватные данные (тексты сообщений,
ключи шифрования) никогда не попадают на сервер и в базу в открытом
виде.** Postgres хранит только: учётки (argon2-хеш пароля), сессии
(`tower-sessions`) и телеметрию передач (тип/размер/успех — без
содержимого) для дашборда. Само сообщение шифруется в браузере (JS,
WebCrypto), кодируется в аудиосигнал в Rust-слое, проигрывается в
динамик — и всё, сервер этого трафика вообще не видит.

## 2. Физический уровень: как данные превращаются в звук

### 2.1 Модуляция — OFDM

Передача построена на **OFDM** (Orthogonal Frequency-Division
Multiplexing) — том же принципе, что лежит в основе Wi-Fi, LTE и DSL.
Идея: вместо одного узкополосного сигнала данные распределяются по
десяткам параллельных поднесущих частот, каждая из которых модулируется
независимо. Это даёт устойчивость к частотно-избирательным помехам
(гулу комнаты, резонансам динамика/микрофона) — если пара поднесущих
«утонет» в шуме, остальные всё равно донесут свою часть данных.

Ключевые параметры (`OfdmConfig::default_48k()`):
- частота дискретизации — 48 000 Гц (стандартная для звуковых карт);
- рабочий диапазон — слышимый спектр (обычная акустика на телефоне/ноутбуке
  без специального железа);
- модуляция поднесущих переключаема: **BPSK** (1 бит/символ, максимальная
  помехоустойчивость) как база и **QAM** более высокого порядка (больше
  бит/символ, но чувствительнее к шуму) — переключение делает `RateAdapter`.

### 2.2 Адаптивная скорость по SNR (Rate Adaptation)

После приёма каждого пакета демодулятор считает отношение сигнал/шум
(`snr_db`) и решает, можно ли поднять модуляцию (перейти на более
«плотное» кодирование, если канал чистый) или нужно откатиться на BPSK
(если приём деградировал). Решение сообщается отправителю управляющим
кадром `RATE` (тип 5 в `proto.rs`): `seq`, `ok`, `modulation`, `snr_db_x10`
(SNR квантуется до десятых долей дБ и укладывается в `i16`). Это
классический механизм ARQ+link adaptation, знакомый по Wi-Fi (802.11
rate control) и модемам xDSL, только реализованный вручную поверх
самодельного аудио-физлевела.

### 2.3 Пакетизация и защита от эха

У акустического канала есть особенность, которой нет у радио: **сигнал,
который вы только что проиграли в динамик, тут же ловится вашим же
микрофоном** (акустическое эхо/просачивание). Поэтому:
- после отправки данных приёмник ожидает служебный ответ (`ACK`/`NAK`/`RATE`)
  не сразу, а сканирует «хвост» записанного буфера (`session::tail_at`) и
  ищет управляющий кадр *позади* эха собственной передачи — приоритет
  отдаётся более «свежим» и более значимым кадрам (`ACK` > `NAK` > `RATE`);
- при приёме есть окно **`ECHO_MUTE` (250 мс)** после отправки
  собственного ответа, чтобы не среагировать на своё же эхо повторно;
- собственный публичный ключ при сопряжении по звуку тоже может
  «эхом» вернуться в микрофон — в `pairing.js` это явно проверяется
  побайтовым сравнением с локальным ключом и отбрасывается.

### 2.4 ARQ (Automatic Repeat reQuest) — надёжность поверх ненадёжного канала

Один «пакет» — это один OFDM-кадр фиксированного максимального размера
(`max_packet_payload`). Большие сообщения/файлы режутся на до
**4095 пакетов** (`MAX_TOTAL_CHUNKS`, ограничение 12-битного поля `seq`
в заголовке). Дальше работает классический скользящий протокол с
подтверждениями:

1. Отправитель проигрывает пакет и слушает `RATE`-ответ на него отдельно
   (до 3 повторов на пакет, `MAX_PACKET_RETRIES`).
2. После отправки всех пакетов отправитель ждёт `ACK(total)` или
   `NAK(total, missing[])`.
3. Если пришёл `NAK` — довозятся только перечисленные недостающие
   номера (`AckLoop::react`), а не всё сообщение целиком.
4. Если таймаут (12 с, `ACK_WAIT`) и нет активной цели довозки — один раз
   выполняется полный повтор передачи (`MAX_FULL_REPLAYS = 1`), затем
   сдача («передано, подтверждение не получено»).
5. Приёмник (`Reassembler`) отбрасывает «протухшие» (`Stale`) и
   дублирующиеся (`Duplicate`) пакеты по монотонному водяному знаку
   позиции в потоке, требует совпадения заявленного `total` во всех
   пакетах одной передачи (`WrongTotal` иначе) — это защита от смешения
   пакетов из разных, не связанных друг с другом передач.
6. По завершении сборки проверяется **SHA-256** содержимого файла
   (у файлов) — если хеш не сошёлся, файл считается повреждённым при
   передаче и не сохраняется на диск.

### 2.5 Ресемплинг и работа с реальным железом

Микрофон и динамик системы редко физически работают ровно на 48 кГц —
драйвер сам выбирает частоту устройства. Слой `resample.rs` делает
линейную интерполяцию между частотой захвата/воспроизведения устройства
(`cap.sample_rate`, определяется через `cpal`) и «модемной» частотой 48
кГц, в обе стороны. Захват идёт в кольцевой буфер в отдельном потоке,
воспроизведение блокирует вызывающий поток до конца проигрывания или
сигнала отмены (`Arc<AtomicBool>` — используется и для кнопок «отменить
передачу»/«остановить приём»).

## 3. ML-фолбэк: когда чистый DSP не справляется

OFDM-демодулятор в `audiodsp` — это классический сигнал-процессинг:
он либо уверенно декодирует пакет, либо честно возвращает «не смог».
На практике акустический канал — самый недружелюбный из всех
(гул кондиционера, скрип стула, отражения от стен, дешёвые динамики
телефонов с завалом АЧХ) — и доля таких «не смог» на слабом сигнале
может быть заметной. Здесь в игру вступает вторая, **ML-линия
обработки** (`model.py`), к которой Rust-сервер обращается как к
крайней мере, если чисто цифровой DSP-путь не вытянул сигнал сам.

### 3.1 Что это за модель

Формально это не «нейросеть» в строгом смысле (без слоёв/backprop), а
**градиентный бустинг** (`sklearn.ensemble.HistGradientBoostingRegressor`) —
но по роли в пайплайне и по духу команда называет её «нейронкой», и
архитектурно она честно выполняет ту же задачу: учится по примерам
превращать «шумный» вход в «чистый» выход. Работает в частотной
области:

1. Аудио режется на окна STFT (`N_FFT = 4096`, `HOP_LENGTH = 1024`,
   `FS = 48000` Гц — та же частота дискретизации, что и у акустического
   модема, не случайно совпадает);
2. из спектрограммы шумного сигнала извлекаются признаки
   (`extract_features`) в рабочей полосе модема **1000–7000 Гц**
   (`BAND_LOW_HZ` / `BAND_HIGH_HZ`) — том самом диапазоне, где живут
   OFDM-поднесущие;
3. регрессор предсказывает «очищенную» амплитуду спектра, фаза
   восстанавливается отдельно, и `stft_to_audio` собирает сигнал
   обратно во времени.

Обучается модель на парах `dataset/train/clean/*.wav` ↔
`dataset/train/noisy/*.wav` (файлы с одинаковыми именами — то есть один
и тот же сигнал, записанный в тишине и с шумом), после чего сохраняется
в `remove_noise_model.pkl` и переиспользуется между вызовами (ленивая
загрузка, один раз в процессе).

### 3.2 Где она включается в общий пайплайн

```
🎙️ приём звука ──► DSP-демодуляция (audiodsp::ofdm) ──► пакет декодирован? ──► ✅ дальше по ARQ как обычно
                                                              │
                                                              │ нет (шум / слабый сигнал)
                                                              ▼
                                            🧠 process_request(сырые байты WAV)
                                            ML-денойзер (model.py, HistGradientBoosting)
                                                              │
                                                              ▼
                                     очищенные байты WAV ──► повторная DSP-демодуляция
                                                              │
                                                     ✅ удалось          ❌ всё ещё не удалось
                                                        │                      │
                                              дальше по ARQ как обычно   пакет уходит в NAK,
                                                                          ждём повтора от отправителя
```

То есть ML-денойзер — это не замена DSP-модему, а **санитайзер входного
сигнала перед повторной попыткой демодуляции**: Rust ничего не решает
«вместо» физики канала, он просто улучшает отношение сигнал/шум там,
где чистая математика Фурье уже не вытягивает, и даёт демодулятору
второй шанс. Это стандартный паттерн «дешёвый быстрый путь → дорогой
ML-фолбэк только по требованию», а не «всё гоняем через модель всегда» —
экономит и время, и CPU, потому что градиентный бустинг заметно тяжелее
FFT-демодуляции.

### 3.3 Контракт между Rust и Python

Со стороны Python интеграция — это одна функция:

```python
from model import process_request

clean_wav_bytes = process_request(noisy_wav_bytes)  # байты WAV → байты WAV, целиком в памяти
```

Никакого чтения/записи файлов на диск при инференсе — только байты
в память и из памяти, что как раз удобно дергать из Rust-сервера как
локальный сервис (конкретный транспорт — sidecar-процесс с HTTP, вызов
через FFI/PyO3 или что-то ещё — зависит от того, как обвязка настроена
на стороне Rust; сама модель об этом ничего не знает и рассчитана на
переиспользование в любом варианте).

Важные эксплуатационные моменты:
- модель **должна быть предварительно обучена** (`python model.py train`)
  до первого обращения с Rust-стороны — иначе `process_request` упадёт
  с `FileNotFoundError: Модель не найдена`;
- обучающий датасет требует **пар файлов с одинаковыми именами** в
  `dataset/train/clean/` и `dataset/train/noisy/` — по имени модель
  сопоставляет «эталон» и «то же самое, но с шумом»;
- зависимости минимальны и не требуют GPU:
  `pip install numpy scipy scikit-learn joblib`;
- есть отдельные CLI-команды для повторной проверки качества уже
  обученной модели (`python model.py test`) и для ручного прогона
  одного файла без Rust вообще (`python model.py denoise in.wav
  out.wav`) — удобно, чтобы на слух сравнить «было / стало», не
  поднимая весь стек.

## 4. Криптография (сквозное шифрование)

Всё шифрование происходит **в браузере**, средствами `WebCrypto`
(`e2e-crypto.js`), сервер и Rust-слой модема работают только с уже
зашифрованными байтами:

1. Каждое устройство при первом сопряжении генерирует пару ключей
   **X25519** (эллиптическая кривая для Диффи—Хеллмана), приватный ключ
   хранится в `localStorage` браузера в формате JWK и никогда никуда не
   передаётся.
2. Публичные ключи **обмениваются по звуку** (см. §2) — руками, по
   очереди («поделиться ключом» / «получить ключ»), с голосовой сверкой
   отпечатка ключа (`fingerprint`, первые 16 байт SHA-256 от общего
   секрета) для защиты от MITM на физическом уровне («это точно ты
   говоришь по телефону рядом со мной, а не кто-то посередине»).
3. Общий секрет считается через ECDH, затем прогоняется через
   **HKDF-SHA256** с солью и `info`-строкой, где к строке подмешаны оба
   публичных ключа в отсортированном порядке (симметрично для обеих
   сторон) — получается 256-битный сессионный ключ AES.
4. Сообщения шифруются **AES-GCM** (IV 12 байт + аутентифицированный тег),
   упаковываются в hex и передаются в модем.
5. Лимит полезной нагрузки одного сообщения — `MAX_PLAINTEXT_BYTES`
   (96 байт минус IV и тег ≈ 68 байт) — заложен потому, что публичный ключ
   при первичном сопряжении должен укладываться в один OFDM-пакет (это
   специально проверяется юнит-тестом `public_key_payload_fits_one_packet`,
   чтобы приёмное «эхо-окно» находило `ACK` сразу за одним пакетом, а не
   искало его среди множества).

Файлы дополнительно проходят через белый список расширений и проверку
magic bytes (`filepolicy.rs`) — расширение файла обязано совпадать с
реально определённым по содержимому MIME-типом (PNG начинается с
`89 50 4E 47…`, JPEG — `FF D8 FF`, и т.д.), плюс отдельно отбрасываются
«двойные расширения» (`invoice.pdf.exe`) как признак маскировки
исполняемого файла.

## 5. Технологический стек

| Слой | Технологии |
|---|---|
| Обёртка приложения | **Tauri 2** (Rust + системный WebView: WebView2 на Windows, WKWebView на macOS/iOS, WebKitGTK на Linux) |
| Веб-сервер | **Axum** (async, поверх `tokio`), шаблоны **Askama** (компилируемые в Rust HTML-шаблоны), сессии — `tower-sessions` + `tower-sessions-sqlx-store` |
| База данных | **PostgreSQL**, запускается как встроенный (`postgresql_embedded`) процесс — отдельно устанавливать СУБД не нужно; миграции — `sqlx::migrate!` |
| Аутентификация | **argon2** (хеширование паролей), куки сессии `HttpOnly` + `SameSite` |
| Аудио/DSP | **cpal** (кроссплатформенный доступ к аудиоустройствам), собственный модуль `audiodsp::ofdm` (модуляция/демодуляция, ARQ-протокол) |
| Криптография | **WebCrypto** в браузере: X25519, HKDF-SHA256, AES-GCM; на Rust-стороне — `sha2` для хешей файлов |
| Фронтенд | Ванильный JS/CSS/HTML без сборщиков и фреймворков — каждая страница подключает нужный набор `<script>` |
| Логирование | `tracing` + `tracing-subscriber` + `tracing-appender` (файл и консоль одновременно) |

Сознательный выбор: **никакого Node.js/Webpack/бандлера на фронтенде** —
статические файлы отдаются как есть через `tower-http::ServeDir`,
что сильно упрощает сборку и уменьшает поверхность атаки/зависимостей.

### 6.9 Что происходит при первом запуске

При первом запуске `bring_up()` в `main.rs` автоматически:

1. Создаёт приватные каталоги в `app_data_dir` (права `0o700` на Unix)
2. Генерирует секреты (`USERNAME_SECRET`, `SESSION_SECRET`, пароль Postgres) и сохраняет их в файлы с правами `0o600`
3. Проверяет и «убирает» зависшие процессы Postgres на нужном порту (`pgcleanup.rs`)
4. Запускает `initdb`/Postgres (с фолбэком на ручной `initdb --locale=C`, если авто-настройка не удалась)
5. Выполняет `sqlx` миграции
6. Поднимает Axum-сервер на `127.0.0.1:8000`
7. Сообщает фронтенду событием `server-ready`

## 7. Запуск на разных платформах

### 7.1 Десктоп (Windows / macOS / Linux) — полностью поддерживается

Собранное приложение — это единый бинарник/бандл, который сам поднимает
локальный сервер, локальную БД и открывает окно с WebView. Установка —
через сгенерированный `cargo tauri build` инсталлятор:
- Windows — `.msi`/`.exe` (NSIS);
- macOS — `.dmg`/`.app` (потребует подписи и нотаризации Apple для
  распространения вне разработческой машины — `codesign` + `notarytool`);
- Linux — `.deb`/`.rpm`/`AppImage`.

### 7.2 Мобильные платформы (iOS/Android) — важные ограничения

В коде явно закреплён факт, что «передача звуком» работает **только**
в нативном Tauri-приложении, а не в обычном браузере
(`AudioModem.unavailableReason` в `native-modem.js`) — потому что доступ
к сырым сэмплам микрофона/динамика на уровне ОС даёт именно `cpal`,
вызываемый из Tauri-команд, а не `Web Audio API`.

Текущая кодовая база (`src-tauri/`, `tauri.conf.json`, зависимости
`cpal`, `postgresql_embedded`) настроена на **desktop targets** Tauri 2
(`--target x86_64-apple-darwin`, `aarch64-apple-darwin`,
`x86_64-pc-windows-msvc`, `x86_64-unknown-linux-gnu` и т.д.). Чтобы
получить полноценный **iOS**-порт, потребуются дополнительные шаги —
Tauri 2 в принципе поддерживает мобильные таргеты, но с оговорками,
специфичными именно для этого проекта:

1. **Тулчейн.** Добавить iOS-таргеты Rust:
   ```bash
   rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios
   cargo install tauri-cli --version "^2"
   cargo tauri ios init
   ```
   Требуется **Xcode** и учётная запись **Apple Developer** (для
   подписи, установки на устройство и тем более для App Store).

2. **Аудио-слой.** `cpal` на iOS работает через `AVAudioEngine`/CoreAudio,
   но:
    - iOS жёстко ограничивает **background audio** (передача не будет
      работать, если приложение свёрнуто, без специального
      `UIBackgroundModes: audio` в `Info.plist`, что тоже не гарантирует
      стабильность длинных ARQ-сессий);
    - нужен явный запрос разрешения на микрофон
      (`NSMicrophoneUsageDescription` в `Info.plist`, Tauri iOS-шаблон
      это поддерживает через `tauri.conf.json → bundle → iOS`);
    - встроенный шумоподавитель/эхоподавитель iOS (по умолчанию
      оптимизированный под звонки) может искажать OFDM-сигнал сильнее,
      чем на десктопе.

3. **Встроенный Postgres на мобильных.** `postgresql_embedded` рассчитан
   на десктопные ОС (скачивает и запускает нативный бинарник Postgres) —
   на iOS запуск произвольных исполняемых процессов запрещён политиками
   песочницы App Store. Для мобильного порта серверную часть (сессии,
   учётки, телеметрию) нужно либо вынести на внешний хост, либо
   заменить на встраиваемую БД (например, SQLite).

4. **WKWebView на iOS** используется автоматически (тот же движок,
